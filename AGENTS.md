# AGENTS.md

## Cursor Cloud specific instructions

This repo is a single product: a **Clothing Order Management System** living under
`clothing-order-system/`. It has two independently-installed npm apps:

- `clothing-order-system/server` — Express + Prisma (PostgreSQL) REST API, ESM, port `4000`.
- `clothing-order-system/client` — React 18 + Vite + Tailwind PWA, dev server on port `5173`.

Target architecture: **Vercel (client) → Render (API) → Neon (PostgreSQL)**. Standard commands
live in each app's `package.json` and in `clothing-order-system/README.md`; prefer those. Notes
below are the non-obvious things.

### Services and how to run them

Three processes are needed for full end-to-end use:

1. **PostgreSQL** (required). Not managed by the app or the update script. It is installed at the
   system level (PostgreSQL 16). Start the cluster before the server, e.g.
   `sudo pg_ctlcluster 16 main start`. A role/db for local dev already exist in the snapshot:
   role `oms` (password `oms`, has `CREATEDB` for Prisma's shadow db) and databases
   `clothing_orders` (dev) and `clothing_orders_test` (tests). The server refuses to boot if
   `DATABASE_URL` is unset.
2. **Server** — from `clothing-order-system/server`: `npm run dev` (uses `node --watch`).
3. **Client** — from `clothing-order-system/client`: `npm run dev` (Vite).

### Environment files (not committed; gitignored)

- `clothing-order-system/server/.env` — copy from `.env.example`. For local dev set
  `DATABASE_URL=postgresql://oms:oms@127.0.0.1:5432/clothing_orders?schema=public`, a `JWT_SECRET`,
  `API_PUBLIC_URL=http://localhost:4000`, and `CORS_ORIGIN=http://localhost:5173`.
- `clothing-order-system/client/.env.local` — `VITE_API_URL=http://localhost:4000`.
  The client talks to the API directly via `VITE_API_URL`; the `/api` dev proxy in
  `vite.config.ts` is unused — don't rely on it.

### Database, migrations, seed (non-obvious)

- Apply schema to a database from `clothing-order-system/server`: `npm run db:migrate:deploy`
  (uses `prisma/migrations`). `npx prisma generate` runs automatically on `npm install`
  (postinstall).
- Seed: `npm run seed` (base reference data — clothing type configs; idempotent) and
  `npm run seed:demo` (demo customers/staff/orders; skips if orders already exist).
- Tests use a **separate** database (`clothing_orders_test`, hardcoded in `tests/setupEnv.js`, or
  override with `DATABASE_URL_TEST`). Apply migrations to it once before running tests:
  `DATABASE_URL="postgresql://oms:oms@127.0.0.1:5432/clothing_orders_test?schema=public" npx prisma migrate deploy`.
  Tests truncate all tables between cases; they never touch the dev database.
- `npx prisma migrate reset` is intentionally blocked for AI agents (destructive). Don't rely on it;
  use `migrate deploy` + seed against a fresh database instead.

### IDs and the API contract (non-obvious)

- Primary keys are 24-char lowercase-hex strings (ObjectId-shaped), generated by a DB default or
  `src/utils/ids.js`. They are exposed to the frontend as `_id` via `src/utils/serialize.js`, so all
  `isMongoId()` validators still pass. Money fields are `Float` (serialize as JSON numbers);
  `measurements` is a JSON column. Auth responses (`/api/auth/*`) intentionally use `id`, not `_id`.

### First user

- There is no signup. Create the first admin via the login screen's "First-time setup" form, or
  `POST /api/auth/bootstrap` with `{email, password (min 8), name}`. Bootstrap only works while the
  users table is empty; after that use `POST /api/auth/login`. The demo seed also creates
  `admin@example.com` / `password123`.

### Testing / building / linting

- Server tests: from `clothing-order-system/server` run `npm test` (Jest + Supertest against the
  test database — start PostgreSQL and migrate the test db first, see above).
- Client build: from `clothing-order-system/client` run `npm run build` (Vite; this is the real
  build gate — the build script does not run `tsc`).
- There is **no** lint tooling (no ESLint, no `lint` script) and no repo-wide typecheck script.
  Note: `npx tsc --noEmit` in `client` currently fails only on a pre-existing
  `"ignoreDeprecations": "6.0"` value in `client/tsconfig.json`; this does not affect `npm run build`.

### Gotchas

- Order creation requires each item to include enum fields `neckType` (`V-shape|square|oval`),
  `handType` (`wide|normal`), and `size` (`adult|kids|baby`); if `measurements` is provided it must
  include `gender` (`female|male|kids`). These are validated at the API boundary and return `400`
  on bad values. Order create/update run in a Prisma transaction, so a failure rolls back cleanly
  (no orphaned orders).
- Uploaded images are stored on local disk under `server/uploads/` (auto-created). This is
  **ephemeral on Render** (lost on redeploy/restart) — production needs S3/Cloudinary.
