## P0

### P0-1 — Saving an order edit wipes garment history and leaves a lying order status

**Screen:** Orders → Edit order (`/orders/ORD-1004/edit` and `/orders/ORD-1003`)  
**Steps:**
1. Create an order with two garments (Thobe + Pants).
2. Scanner: lookup `ORD-n-1`, pick Cutter Sam, **Scan in to received**, **Scan out / complete received**, **Scan in to cutting**.
3. Confirm timeline has RECEIVED completed + CUTTING in progress (`GET /api/order-items/:id/timeline` → 200, 2 stages).
4. Edit order. Change only a note (or nothing material). Click **Save changes**.

**Expected:** Same item IDs, barcodes, checkpoints, assignments, images. Status still matches remaining work.  
**Actual:**
- Item IDs are new (`4e47df2a…` → `bd320d9c…`). Old timeline `404 Order item not found`.
- Checkpoint count on both garments → `0`. Next stage resets to RECEIVED / WAITING / Unassigned.
- `Order.productionStatus` stays **`cutting`** because the form re-submits the old status and PUT does not re-sync from (now empty) stages.
- Cutter Sam stays **BUSY** with **0 active assignments** (`presence: idle`).
- Order-level production logs (scan in/out, “Synced from furthest stage CUTTING”) are **not** deleted, so Overview “Recent activity” still claims CUTTING after the garments have been reborn as unstarted.

Reproduced twice: API PUT mimicking the UI (`ORD-1003`) and the Edit UI (`ORD-1004`). Server: `replaceItemsForOrder` in `server/src/routes/orders.js` (“Deleting items cascades their images, checkpoints and assignments”). Client always PUTs `items: [...]` from `OrderEditPage`.

**Evidence:** `qa_put_wipe_stale_cutting_vs_waiting.png`, `qa_edit_save_wiped_history.png`, `qa_api_probe.json`

## P1

### P1-1 — Live floor path is not Christian’s operating path

**Screen:** Floor, Scanner, Overview pipeline  
**Christian (source of truth):**  
UNASSIGNED → RECEIVED *(manager assignment only, not a workstation, not a scan)* → SEWING & CUTTING → EMBROIDERY → FINAL SEWING / ASSEMBLY → FINISHING → SHOWROOM / COMPLETED *(per garment, 3/5 until 5/5)* → READY TO PACK *(all complete)* → READY FOR PICKUP / DELIVERY.

**Actual on main:** `RECEIVED → CUTTING → SEWING → EMBROIDERY → FINISHING → PACKAGING → READY → DELIVERED`  
UI labels are lowercased (`received`, `cutting`, …). Floor copy: “Check in → working → check out → next stage. Scanning moves the garment.”

**Gaps:** no UNASSIGNED column (unassigned is a badge on RECEIVED cards); RECEIVED is a timed scan-in/scan-out workstation; CUTTING and SEWING are separate, not “SEWING & CUTTING”; no FINAL SEWING / ASSEMBLY; no SHOWROOM with n/m; PACKAGING / READY / DELIVERED do not match READY TO PACK / PICKUP.

### P1-2 — RECEIVED is a scan workstation; first scan requires a RECEIVED-skilled worker

**Screen:** Scanner (`/scan?barcode=ORD-1004-1`)  
**Steps:** Lookup a new garment.  
**Expected:** Manager assigns/hands over; first **workstation scan** is cutting/sewing. RECEIVED is assignment state only.  
**Actual:** Primary action **Scan in to received** (disabled until a worker is selected). Manager command: “Assign Received, then scan in.” `GET /api/staff?stage=RECEIVED` returns **only Cutter Sam** (demo tailor/embroiderer/finisher hidden). After check-in: **Scan out / complete received**, Where = “Received Workstation”.

**Evidence:** `qa_scanner_scan_in_to_received.png`

### P1-3 — Order status follows the furthest sibling (no n/m)

**Screen:** Orders list, order detail, Overview  
**Steps:** Two-garment order. Advance only garment 1 into CUTTING. Leave garment 2 unstarted.  
**Expected:** Order does not read as fully in cutting. Show per-garment progress (e.g. 1/2 cutting, 1/2 unstarted) until READY TO PACK when all are complete.  
**Actual:** List badge **CUTTING**. `productionStatus=cutting` while item 2 is `next: RECEIVED`, `board: waiting`. Floor still shows both cards (see P1-3 vs hide-siblings).

**Evidence:** `qa_floor_siblings_still_visible.png`, orders list `05_orders_list.png` (ORD-1003 CUTTING after only one item had been advanced — and later after wipe still CUTTING).
